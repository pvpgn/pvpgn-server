# Plan: real password verification for WC3 1.29 + PvPGN

Companion to `wc3-1.29-pvpgn-notes.md`. That doc covers what we did to
get the dev-mode bypass working. **This doc is the plan to replace the
bypass with real authentication**, modelled on the
[W3CE](https://github.com/Warcraft-III-Community-Edition/Launcher)
launcher v0.2.1-alpha.

## Why this is needed

Our current setup (committed in `wc3-1.29-support` branch) authenticates
nothing:

- Server: `if (conn_get_client_proof(c))` — accepts any 20-byte M1 the
  client sends.
- Client: 4 NOP'd JNEs around the M2 verifier — accepts any M2 the
  server sends.

Both sides bypass the SRP3 cryptographic check. Anyone can log in to any
existing account. Useful for a single-user dev box; unshippable for
anything multi-user.

The proper fix is hard because PvPGN's SRP3 implementation is known
working for 1.27/1.28 but not for 1.29 (some divergence in M1 inputs we
never identified — probably MD5 vs SHA-1, see notes §6). Rather than
fix SRP3 we do what W3CE does: make the client behave as a pre-SRP3
client and use PvPGN's existing `passhash1` legacy code path.

## What W3CE does (analysis of v0.2.1-alpha)

Architecture: `W3CE.Launcher.exe` (.NET 6) does:

1. Verify input EXE MD5 == `c4 53 b4 a0 bd e1 a4 7f 41 cb 24 75 57 3e
   db 84` (= 1.29.2.9231 vanilla) **OR** `5f 13 0a 47 63 f1 18 9d 32 86
   d8 91 f6 b0 5f 7c` (= same EXE with the LAA bit flipped). Refuse
   anything else.
2. If input is the vanilla MD5, copy to `Warcraft III Patched.exe` and
   set 2 PE-header bytes to enable the `IMAGE_FILE_LARGE_ADDRESS_AWARE`
   flag (so the game can use 4 GB instead of 2 GB on 64-bit Windows).
3. `CreateProcess(SUSPENDED)` the patched EXE.
4. Allocate the path of `W3CE.Loader.dll` in the suspended process,
   `CreateRemoteThread(LoadLibraryA, that_path)`.
5. `W3CE.Loader.dll` is a native bootstrap DLL that hosts the .NET 6
   runtime and loads `W3CE.dll` (managed) into the process.
6. `W3CE.dll`'s `PvPGNPatcher` constructor runs:

```csharp
// from W3CE.dll, decompiled with ilspycmd
public unsafe PvPGNPatcher(ReloadedHooks hooks)
{
    // Byte patches - applied to memory of the loaded EXE
    byte[] buffer = new byte[6] { 102, 15, 31, 68, 0, 0 };
    Memory.Write(Module.ToModule(8590372u), buffer);     // VA 0x00831424 = our auth_req
    byte[] buffer2 = new byte[2] { 117, 32 };
    Memory.Write(Module.ToModule(8588763u), buffer2);    // VA 0x0083045B (jz->jne)

    // Runtime function hooks - replace function bodies via Reloaded.Hooks
    lphCheckedHook = hooks.CreateHook<LPHCheckedPrototype>(
        LphChecked, Module.ToModule(8627600u).ToInt64()).Activate();   // VA 0x00831F90
    createAccountHook = hooks.CreateHook<CreateAccountPrototype>(
        CreateAccount, Module.ToModule(9988688u).ToInt64()).Activate(); // VA 0x00987F50
}
```

Function signatures (from same decompile):

```csharp
[Function(CallingConventions.Cdecl)]
unsafe delegate int LPHCheckedPrototype(byte* a1, char* a2, int a3, int a4);

[Function(CallingConventions.MicrosoftThiscall)]
unsafe delegate int CreateAccountPrototype(void* t, void* username, byte* password, byte* a4, int a5);
```

Hook bodies:

```csharp
private unsafe int LphChecked(byte* a1, char* a2, int a3, int a4)
{
    // Read password (ASCII, null-terminated) from a2 + 32, lowercase it,
    // run W3CE.PvPGNHash.CalculateHash (which is bnet_hash from PvPGN's
    // src/common/bnethash.cpp), write 20 bytes to a1, return 1.
    byte[] hash = PvPGNHash.CalculateHash(
        Marshal.PtrToStringAnsi((IntPtr)a2 + 32).ToLower());
    for (int i = 0; i < hash.Length; i++) a1[i] = hash[i];
    return 1;
}

private unsafe int CreateAccount(void* t, void* username, byte* password,
                                 byte* a4, int a5)
{
    int result = createAccountHook.OriginalFunction(t, username, password,
                                                    a4, a5);
    // After the original ran, copy the plaintext password into the
    // verifier field at a4[32..47]. PvPGN's _client_createaccountw3
    // detects the printable bytes and falls into the `presume_plainpass`
    // path - which derives the SRP3 verifier server-side AND sets
    // passhash1 = bnet_hash(plaintext). The plaintext stays in memory on
    // the server momentarily, isn't logged.
    for (int i = 0; i < 16; i++) a4[32 + i] = password[i];
    return result;
}
```

`PvPGNHash.CalculateHash` is W3CE's C# port of PvPGN's
`bnet_hash` (`src/common/bnethash.cpp`). It is a modified SHA-1: pad the
input to 1024 bytes (wait, actually PvPGN's reference impl pads to 64
bytes per round — W3CE allocates a fixed 1024-byte buffer big enough for
the largest input it'll see), build a 64-entry expansion via a custom
mixing function (`ROL(1, x ^ y ^ z ^ w)` — note the `1`, not the input
bit), then 4×20 SHA-1 rounds. Output: 20 bytes (5 dwords).

## Why it works against PvPGN unchanged

`src/bnetd/handle_bnet.cpp:_client_logonproofreq` has *two* compare
paths after the M1 packet arrives:

```cpp
// SRP3 path (line ~2240)
if (conn_get_client_proof(c) && memcmp(client_password_proof,
                                       conn_get_client_proof(c), 20) == 0) {
    // success via SRP3
}
// Legacy passhash1 path (line ~2258)
else if (hash_eq(clienthash, serverhash)) {
    //                ^- received 20-byte M1 reinterpreted as a hash
    //                              ^- account_get_pass(account) = passhash1
    // success via legacy
}
```

When the W3CE-patched client sends `bnet_hash(plaintext_password)` as
the M1, the SRP3 compare fails (PvPGN's SRP3 M1 is computed from the
verifier, not bnet_hash). It falls through to `hash_eq` which compares
`clienthash` (= what the client just sent = `bnet_hash(plaintext)`)
against `serverhash` (= `passhash1` = `bnet_hash(plaintext)` written
during create-account when `presume_plainpass` triggered). They match,
login succeeds, no PvPGN code change needed.

## Our plan: a minimal port

We don't want to ship .NET, Reloaded.Hooks, or a full DLL injector
inside `pvpgn-server`. The minimum equivalent:

### Minimal scope

Two hooks to install. Both can live as code in a new section we append
to `Warcraft III.exe`.

1. **`LphChecked` replacement** at VA `0x00831F90`. Replace function
   body with a stub that:
   - Reads ASCII password from `[arg2 + 32]`.
   - Lowercases (ASCII only — passwords with high-bit chars not
     supported in this minimal version).
   - Calls our embedded `bnet_hash`.
   - Writes 20 bytes to `[arg1]`.
   - Returns `1`.
   - Stack cleanup: `ret 0x10` (4 args × 4 bytes; but verify signature
     by disassembling the original function's epilogue first).

2. **`CreateAccount` wrapper** at VA `0x00987F50`. This one needs a
   trampoline because we have to call the original. Plan:
   - Save the first ~5-7 bytes of the original function to a trampoline
     buffer in our code cave.
   - Append a `JMP back-to-original+5` after the saved bytes.
   - Replace original first 5 bytes with `JMP our_wrapper`.
   - Our wrapper saves args/regs, `CALL trampoline` (which executes
     the saved prologue and returns to our wrapper at the original+5
     position via the JMP), gets the return value, copies the plaintext
     password from `arg3` into `arg4 + 32 .. arg4 + 47`, returns.
   - This is __thiscall: `this` in `ECX`, args `username, password, a4,
     a5` on the stack (right-to-left).

### Implementation path

| Step | Tooling |
| ---: | :--- |
| Implement `bnet_hash` in C, ~80 lines | gcc -m32 -ffreestanding -fno-stack-protector -O2 -S to get x86 assembly |
| Hand-write the two hook stubs in x86 assembly | keystone-engine (already installed in venv) |
| Find code-cave location | new section appended after `.reloc`, or extend `.text` (preferred: new section for clarity, ~4 KB enough) |
| Patch PE headers to declare the new section | pefile (already installed) |
| Patch the two function entries to JMP to our cave | python writer |
| Generate final patched EXE | one Python script, similar to current `patch-client.ps1` |

Output: a single `.exe` file. No DLL, no loader, no runtime. The
patched EXE behaves like the original except the SRP3 dance is
short-circuited to bnet_hash. Server side: revert the M1 bypass,
remove diagnostic eventlogs, leave everything else as upstream PvPGN.

### What we explicitly are NOT doing

- **No LAA flag.** W3CE flips the LAA bit; we don't need to. Players
  who care about 4 GB can apply LAA separately; we keep our patch set
  focused on auth.
- **No Unicode passwords.** ASCII only. Limits us but matches the
  existing PvPGN constraint anyway (passhash1 is ASCII-lowercased
  before hashing in `_client_createaccountw3`).
- **No anti-hack / map-validation hooks.** W3CE has many of these;
  irrelevant to auth.
- **No telemetry suppression hooks.** Not needed for our purposes.
- **No `0x0083045B` byte patch (the W3CE second one).** Its effect
  isn't auth-critical — likely an unrelated game-flow tweak. Skip
  unless we discover we need it.

### Risks / open questions

1. **Function signatures.** The W3CE prototype has `LphChecked` as
   `__cdecl` taking 4 args (`byte*, char*, int, int`). The native
   function might actually be `__thiscall` or `__fastcall` — W3CE's
   prototype is what `Reloaded.Hooks` was told to use, which only has
   to match for the trampoline replacement to work. Our hand-written
   stub needs the *real* convention. Plan: disassemble around the
   original's prologue/epilogue to confirm `ret 0x10` (cdecl/stdcall
   with 4 stack args) vs `ret 0xc` (3 stack args + `this`) etc.

2. **Where the "password" lives in `LphChecked`'s arg2 struct.** W3CE
   reads `(IntPtr)a2 + 32` and treats it as a null-terminated ANSI
   string. The "+32" is the offset inside the struct that the function
   receives. We have to verify this still holds — drop a debug print in
   the eventlog from the server side that shows what bytes the client
   sends as the M1, with our hook patched to send `(input_struct +
   0..40)` byte dump first, to confirm the password really is at +32.

3. **The original prologue at `0x00831F90`.** Disassembly looked like
   `c0 ff 83 c4 10 8d 8b ...` which decodes oddly. Possibilities: (a)
   we're reading the wrong byte boundary (the function actually starts
   a few bytes earlier or later), (b) the function has SEH unwinding
   data in the first bytes, (c) it's hot-patchable padding from MSVC
   (`/hotpatch` flag emits `mov edi, edi` = `8B FF` first). Need to
   confirm the actual function start before patching.

4. **`bnet_hash` correctness.** PvPGN's `bnet_hash` has a quirky
   16-byte-block expansion in `hash_set_16` with `do_blizzard_hash`
   variant — it stores bytes in little-endian dword order, NOT
   big-endian. Our C port must use that variant exactly. W3CE's
   `PvPGNHash.SafeHash` is the reference; PvPGN's `bnet_hash` +
   `hash_set_16(do_blizzard_hash)` is the canonical source of truth.

5. **Code-cave location.** The PE has `SizeOfImage = 0xebb000` after
   the existing 8 sections. Adding a new section bumps the section
   count (header byte at `e_lfanew + 6`) and requires a fresh
   `IMAGE_SECTION_HEADER` row. Need to verify there's room in the
   header padding — if `SizeOfHeaders = 0x400` and used header bytes
   stop well below that, adding 40 bytes for one more section header
   row should fit. If not, we'd need to bump `SizeOfHeaders` and
   reflow the file alignment, which is messier.

## Server-side cleanup once the client is real-auth

When the client patcher above is working:

- `src/bnetd/handle_bnet.cpp:2240` — revert the dev bypass, restore
  the original `if (... && memcmp(...) == 0)` branch. Keep the legacy
  `hash_eq` fallback (which is what catches our bnet_hash).
- `src/bnetd/handle_bnet.cpp:2249` — revert the forced
  `RESPONSE_OK`, restore the `RESPONSE_EMAIL` branching (for accounts
  without an email).
- `src/bnetd/handle_bnet.cpp:~700` and `~2225` — remove the two
  diagnostic eventlogs.
- After all the reverts, the only remaining server-side change in the
  branch is `conf/versioncheck.json.in` (the `0x1d` rows) and the
  `motdw3` `{fmt}` bugfix in `handle_bnet.cpp:2951`. Both are clean,
  upstream-mergeable.

## File layout for the new code

Proposed structure under `contrib/wc3-1.29-client-patch/`:

```
contrib/wc3-1.29-client-patch/
├── README.md                       (existing — update to describe new mode)
├── patch-client.bat                (existing — keep as the entry point)
├── patch-client.ps1                (existing — the bypass-mode patcher)
├── patch-client-real-auth.ps1      (new — the real-auth patcher)
├── bnet_hash.c                     (new — C reference impl, for review)
├── hooks.asm                       (new — the two hook stubs in NASM-ish syntax)
└── build-payload.py                (new — assembles bnet_hash + hooks into a code cave blob)
```

`build-payload.py` runs on Linux and produces a `payload.bin` that
`patch-client-real-auth.ps1` injects into the EXE as a new section.
The PowerShell side stays simple — it knows where to splice and what
function entries to redirect, but the actual machine code comes from
the Linux-side build.

## Testing

1. Apply the new patcher to a fresh `Warcraft III.exe`.
2. Revert the server-side bypass.
3. Wipe the `users/user1` (or whatever) account.
4. Create a new account with password `mypass`.
5. Server should log a `passhash1` derived from `mypass`, plus salt +
   verifier (`presume_plainpass` triggered). Verify by reading
   `var/pvpgn/users/<name>` and confirming `passhash1` is non-empty
   and not the `67452301efcdab8998badcfe10325476c3d2e1f0` "empty SHA-1"
   sentinel we kept seeing.
6. Log out, log back in with `mypass`. Server should log
   "logged in (right client password proof)" via the **legacy**
   `hash_eq` path, not the SRP3 path.
7. Try logging in with a wrong password — should be rejected.
