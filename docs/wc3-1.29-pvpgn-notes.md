# Connecting Warcraft III 1.29.2 to PvPGN — implementation notes

This document captures everything found while making a vanilla Warcraft III
1.29.2.9231 client log into a local PvPGN server. It is meant for the next
person who wants to extend support to other 1.29.x sub-versions, port the
client patches into a `dll_29` helper, or upstream a versioncheck row.

**Status: end-to-end working with real password authentication.** A
1.29.2.9231 client patched with `contrib/wc3-1.29-client-patch/build_payload.py`
logs into PvPGN with a proper password check via the legacy `passhash1`
code path. The original SRP3-protocol divergence between PvPGN and 1.29
is *sidestepped* rather than solved (W3CE-style: client emits
`bnet_hash(password)` instead of an SRP3 M1, PvPGN's existing
`hash_eq(clienthash, serverhash)` legacy fallback validates it). No
server-side cryptographic bypass is in tree; the only server-side delta
is the `0x1d` versioncheck row and a pre-existing `{fmt}` crash fix.

This document is the historical analysis and stepping-stone bypass-mode
notes. For the real-auth design and how it works, see
`docs/wc3-1.29-real-auth-plan.md`.

## 2. Client gateway redirect

WC3's Battle.net dialog has no UI for entering a custom server. To redirect
the client at a non-Blizzard server, write a `bnserver-WAR3.ini` file:

```ini
[Server List Version]
VER=1001

[Server Gateways]
1=192.168.1.223

[192.168.1.223]
ZONE=0
ENU=Local PvPGN
```

**Important: 1.29 reads this file from `<install>\BattleNet\bnserver-WAR3.ini`,
not from the install root.** This differs from earlier 1.x versions that
looked next to the EXE. The exact path is hardcoded in the binary; the
literal string `"BattleNet\bnserver-WAR3.ini"` appears at file offset
`0x00a8b9fc` (VA `0x00e8cbfc`) and is referenced once at VA `0x00545207`.

The legacy `bnserver-WAR3.ini` location (next to the EXE) is silently
ignored on 1.29 — the in-game gateway list shows Blizzard's defaults
because the file is never opened.

The gateway-list config-format strings `battlenet_V0`, `battlenet_V1`, and
`bnetGateway` (all in `.rdata`) hint at two parser variants but both feed
the same `CBattleNetGateways` class.

## 3. Versioncheck (CheckRevision)

The 1.29 client connects to TCP/6112 and sends `SID_AUTH_INFO` with:

```
protocol  = 0x0
platform  = IX86
product   = W3XP            (Frozen Throne — used even for ROC in 1.29)
versionid = 0x1d            (verbyte; not in any pre-1.29 PvPGN release)
language  = enUS
```

The PvPGN lookup at `select_checkrevision` in
`src/bnetd/versioncheck.cpp:208` keys on `(architecture, client, version_id)`
which translates to `(IX86, W3XP, 0x1d)`. Until a row exists with that key,
the lookup falls through to the bogus default
`A=42 B=42 C=42 4 A=A^S B=B^B C=C^C A=A^S` and the client disconnects
without responding.

**A `0x1d` row must exist under both the `WAR3` and `W3XP` top-level blocks
in `conf/versioncheck.json.in`.** The 1.29 unified launcher reports
`product=W3XP`; the `WAR3` row is for symmetry / future ROC clients.

The verbyte's CheckRevision equation appears unchanged from 1.28
(`A=1239576727 C=1604096186 B=4198521212 4 A=A+S B=B-C C=C^A A=A+B` with
`ver-IX86-1.mpq`). The 1.29 client does not ship `ver-IX86-1.mpq` locally;
it downloads it from the server during the file-upgrade phase
(immediately after `SID_AUTH_CHECK`). PvPGN already serves it from
`var/pvpgn/files/ver-IX86-1.mpq`, so no extra config is needed.

The CheckRevision result observed from the test client is:

```
verstr      = 1.29.2.15
exeinfo     = "Warcraft III.exe MM/DD/YY HH:MM:SS 14854632"   (date varies)
gameversion = 0x011d020f
checksum    = 0x3cc7eaf6
```

That `checksum` is what goes in the `hash` field of the versioncheck entry.

The full row added (under `W3XP` and mirrored under `WAR3`):

```json
"0x1d": {
    "checkRevisionFile": "ver-IX86-1.mpq",
    "equation": "A=1239576727 C=1604096186 B=4198521212 4 A=A+S B=B-C C=C^A A=A+B",
    "entries": [
        {
            "title": "Warcraft III - TFT 1.29.2",
            "version": "1.29.2.15",
            "hash": "0x3cc7eaf6",
            "fileMetadata": "Warcraft III.exe 05/01/18 18:19:51 14854632",
            "versionTag": "W3XP_1292"
        }
    ]
}
```

## 4. The 128-byte server signature (auth_req patch)

In `SERVER_AUTH_INFO_REPLY` (a.k.a. `SERVER_AUTHREQ_109`, packet ID `0x50`),
PvPGN appends 128 bytes of `\0` where Blizzard's RSA-signed server
signature would normally go. See `src/bnetd/handle_bnet.cpp:610-616`:

```cpp
if (conn_get_clienttag(c) == CLIENTTAG_WARCRAFT3_UINT
    || conn_get_clienttag(c) == CLIENTTAG_WAR3XP_UINT) {
    char padding[128];
    std::memset(padding, 0, 128);
    packet_append_data(rpacket, padding, 128);
}
```

PvPGN does not have Blizzard's RSA private key, so it cannot generate a
real signature. Vanilla 1.29 verifies that signature against an embedded
`BLIZZARDKEY` and disconnects on mismatch. **Every public PvPGN deployment
relies on every WC3 client being patched to skip this check.**

In w3l terminology this is the `auth_req` patch. The 1.28 reference
signature from `../w3l/dll_29/patches.h` is the inlined memcmp loop:

```
8B 01 3B 02 0F 85 C5 00 00 00 83 C1 04 83 C2 04 83 EE 04 73 EB
```

The same instruction sequence is present in 1.29 with one byte different
(the JNE displacement) at VA `0x00831424`:

```
0x00831420  8B 01           mov  eax, [ecx]
0x00831422  3B 02           cmp  eax, [edx]
0x00831424  0F 85 B8 00 00  jne  0x008314e2          ← target
0x0083142a  83 C1 04        add  ecx, 4
0x0083142d  83 C2 04        add  edx, 4
0x00831430  83 EE 04        sub  esi, 4              ; esi starts at 0x80 = 128
0x00831433  73 EB           jae  0x00831420
```

Function start at `0x00831300` features six `push 0x80` setting up two
128-byte buffers (the received signature and the expected signature). It is
a `__thiscall` member function with one xref at `0x0082fc99`. The fail
target `0x008314e2` does `xor eax, eax; ret 0x10` (returns FALSE).

**Patch: NOP the JNE.** Replace the 6 bytes of `jne` with a 6-byte
multi-byte NOP (the canonical `nop word ptr [eax + eax + 0]`):

| Field | Value |
| ---: | :--- |
| File offset | `0x00430824` |
| Original    | `0F 85 B8 00 00 00` |
| Patched     | `66 0F 1F 44 00 00` |

After this patch the loop's `jne` is harmless; the loop runs through 33
iterations (132 bytes — 4 past the buffer end, but still on a mapped
page) and falls through to the success path that returns TRUE.

## 5. SRP3 logon proof — the unsolved gap

After the version-check, the client opens the
`SID_AUTH_ACCOUNTLOGON`/`SID_AUTH_ACCOUNTLOGONPROOF` SRP3 dance. PvPGN's
SRP3 is implemented in `src/common/bnetsrp3.cpp` and is known to work for
1.27 and 1.28 clients. **For 1.29 it does not.**

Observed behaviour:

- Account creation succeeds: client sends a real 32-byte salt + 32-byte
  verifier, PvPGN persists them via `account_set_salt` /
  `account_set_verifier` (raw 32-byte attributes).
- Login fails at the M1 comparison in `handle_bnet.cpp:2240` with
  `got wrong client password proof for "<user>"`.
- Same password used at create + login. Mismatch is consistent across
  retries — not a typing error.

Diagnostic eventlog calls were added (still in tree, see §8) that print
`client_sent` and `server_expected`. Sample output:

```
client_sent     = 9557d74a7db0e750081e8b4fad31765dcebb6004
server_expected = 20cb175fdfacab2653239ef6999f9733308b9671
```

Both are valid SHA-1 hashes; both are non-trivial; they are simply not
the same value. Same password, same salt, same A and B (both sides
exchanged them on the wire).

### Hypotheses checked

| Hypothesis | Result |
| :--- | :--- |
| PvPGN uppercases username/password in `BnetSRP3::init`; 1.29 doesn't | Disabling uppercase did **not** change the mismatch |
| PvPGN uses different `N` modulus | N is identical (PvPGN stores big-endian, 1.29 stores little-endian, but the *integer* is the same) — found in 1.29 binary at `.rdata` offset `0x00abcc84` byte-reversed |
| PvPGN uses different `g` | Both use 47 (`0x2F`) per BNCS spec |

### Hypotheses not yet checked

1. **`bnetsrp3_I`** (the 20-byte constant `H(N) XOR H(g)`, used as the
   first input to M1). PvPGN hard-codes `F8 01 8C F0 A4 25 BA 8B EB 89 58
   B1 AB 6B F9 0A ED 97 0E 6C`; this 20-byte value is **not** present in
   the 1.29 binary in either order. The client likely computes it at
   runtime from N and g — and may use different SHA-1 conventions
   (little-endian vs big-endian).

2. **SRP variant.** PvPGN uses SRP-3 with `u = first 32 bits of SHA1(B)`
   (see `BnetSRP3::getScrambler`). 1.29 may use SRP-6/6a with
   `u = H(A | B)` and a non-trivial multiplier `k`.

3. **Hash-input byte ordering.** PvPGN mixes
   `little_endian_sha1_hash` (for proof inputs) and `sha1_hash` (for
   scrambler). 1.29 may have flipped the convention on one of these.

Confirming any of these requires disassembling the 1.29 client's M1
computation — which is in a function not yet located. The vtable
analysis in `/tmp/find_lph_state.py` showed that the
`CONNSTATE_AUTH_*` strings live in a flat lookup table at VA
`0x0082af6c..0x0082afc4` (each entry is the address of a tiny
`mov eax, <stringptr>; pop ebp; ret` stub) — **not** a C++ vtable.
Dispatch is done via switch/array index, not virtual calls, which means
state-handler discovery via xref-from-vtable doesn't work.

### Workaround currently in tree

`src/bnetd/handle_bnet.cpp:2240` has been changed from

```cpp
if (conn_get_client_proof(c) && std::memcmp(client_password_proof, conn_get_client_proof(c), 20) == 0) {
```

to

```cpp
/* TEMP: dev bypass for 1.29 SRP3 incompatibility - accept any M1 */
if (conn_get_client_proof(c)) {
```

This makes PvPGN accept any M1 the client sends. The success path then
sends the server's (cryptographically wrong, but format-valid) M2 back
to the client. That triggers the next problem (§6).

## 6. The M2 verifier (lph_verify patch)

Once PvPGN accepts the (wrong) M1 and sends back its own (wrong) M2, the
1.29 client validates the server's M2 against what it would expect under
its own SRP3 derivation. They differ → client tears down the TCP
connection silently after `SERVER_LOGONPROOFREPLY`.

In w3l terminology this is the `logon_proof_hash_verify` patch. The
1.28 reference patch was a 1-byte JZ→JNE flip at the call site
identified by:

```
8D 8E 2C 04 00 00 8D 95 68 FF FF FF E8 ?? ?? ?? ??
8B CE 85 C0 74 20 6A 0C
```

This pattern does **not** appear in 1.29 in any form (strict, masked,
loose). The compiler in 1.29 either inlined the verify call or moved
its call site elsewhere.

### Locating it via memcmp signature

The same approach used for `auth_req` (find a 20-byte memcmp loop tail
`83 ?? 04 73 ??`, narrow to functions whose prologue contains a
`mov esi, 0x14` length setup) returned 7 candidates. Investigation:

| VA | Notes |
| ---: | :--- |
| `0x0078e240` | 20-byte memcmp returning **0** on equal — generic memcmp library function. Patched in the working build (probably harmless, may be unused on this code path). |
| `0x007d3980` | 20-byte memcmp + sets `[edi+0x52c] = 0/1` flag; returns `ret 4`. NOPping its JNE alone did **not** unblock login. Patched in the working build. |
| `0x00917f70` | Two 20-byte memcmps in one function; NOPping both alone did **not** unblock login. Patched in the working build. |
| `0x00986b40` | 16-byte memcmp after a hash chain (MD5-shaped: init/update×3/finalize). Inputs total 92 bytes (= 32 + 20 + 40, the size of an SRP3 M2 input `A | M1 | K`). Patched in the working build. |
| `0x00a16980` | Larger function with `push 5` (5 dwords = 20 bytes), different shape. Not patched. |
| `0x00a292b0` | Larger function with `push 5`, different shape. Not patched. |

The current working build patches **all 5 candidates with a length-20
or length-`(0x14)` setup** at once (one of them is the actual M2 verifier;
the others are NOPped out of an abundance of caution and have not caused
any observable misbehaviour). Bisection to find the single load-bearing
patch has not been done.

The patch is identical at each site: the JNE that bails on memcmp
mismatch becomes two NOPs, so the loop falls through unconditionally
into the success path. Sites and original bytes:

| Name           | VA           | File off    | Original | Patched |
| :------------- | -----------: | ----------: | :------- | :------ |
| `lph_v_7d3980` | `0x007d39b4` | `0x003d2db4` | `75 1B` | `90 90` |
| `lph_v_917ff7` | `0x00917ff7` | `0x005173f7` | `75 19` | `90 90` |
| `lph_v_918076` | `0x00918076` | `0x00517476` | `75 0F` | `90 90` |
| `lph_v_986bb4` | `0x00986bb4` | `0x00585fb4` | `75 21` | `90 90` |

(Plus `auth_req` from §4. `lph_v_78e254` at VA `0x0078e254` was not
patched in the final working build. Note: an earlier theory pegged
`0x007d3980` as "the" verifier based on its `[this+0x52c]` flag pattern
— that flag is real but writing it with the right value alone wasn't
enough; the actual disconnect signal must come from a different site
that one of the other three candidates blocks.)

The strongest single hypothesis — based on input lengths matching the
SRP3 M2 derivation `H(A | M1 | K)` exactly (32 + 20 + 40 = 92 bytes,
giving a 16-byte MD5-style output) — is **`0x00986b40`**, the only
candidate that shows a hash-chain build-up rather than a raw memcmp.
That suggests 1.29 may verify M2 with MD5 (or a 16-byte digest derived
from a non-standard hash) rather than SHA-1, which would also explain
why PvPGN's SHA-1 M2 always fails — they're not even the same hash
function. This has not been confirmed; bisecting the patch set would
prove or disprove it.

## 7. Server-side state

### Permanent

- `conf/versioncheck.json.in` — added `0x1d` rows under both `WAR3` and
  `W3XP` blocks (see §3). Run `make install` after editing to regenerate
  `build/stage/etc/pvpgn/versioncheck.json`. bnetd does not reload
  versioncheck on SIGHUP — full restart is required.

- `src/bnetd/handle_bnet.cpp` line ~2951 — **bugfix** (independent of
  1.29 work): `fmt::format_to(serverinfo, "{}" + '\n', (line + 1));`
  was C++ pointer arithmetic, not string concatenation. It only fired
  the first time bnetd parsed `bnmotd_w3.txt` and crashed the daemon
  with `FATAL ERROR: argument index out of range` from `{fmt}`. We hit
  it because the 1.29 client got far enough to request the W3 MOTD.
  Fixed to `"{}\n"`. See §10.

### Historical (no longer in tree)

During the bypass-mode development phase that preceded this branch,
the following temporary changes lived in `src/bnetd/handle_bnet.cpp`:

- diagnostic eventlogs in `_client_createaccountw3` and
  `_client_logonproofreq` dumping salt, verifier, and proof bytes;
- a dev-mode M1 bypass that accepted any client proof;
- a forced `RESPONSE_OK` that ignored the `RESPONSE_EMAIL` branch.

All three have been reverted. They live in the
`wc3-1.29-bypass-mode` branch on the fork if you want to see the
intermediate steps; the current branch tree is clean against upstream
on these lines.

`src/common/bnetsrp3.cpp`: an experimental change to disable username/
password uppercasing was tried and reverted — current tree is identical
to upstream.

## 8. What was learned

This bypass-mode document was the stepping-stone to the real-auth
solution that's actually shipped on this branch. The approach we
ended up with (see `docs/wc3-1.29-real-auth-plan.md` and
`contrib/wc3-1.29-client-patch/`) is W3CE-style — patch the client to
emit `bnet_hash(password)` where SRP3 would have sent its M1, plus
the create-account hook that copies plaintext into the verifier slot.
PvPGN's existing legacy `passhash1` `hash_eq` path validates the
result without any server-side cryptographic bypass.

The bisection step in earlier drafts of this section turned out
unnecessary: the W3CE-style approach replaces the M1 computation
itself rather than NOPping the M2 verify, so the multi-NOP shotgun
patch from bypass mode is no longer applied.

## 9. Open questions / future work

1. **Investigate other 1.29.x sub-versions.** The CheckRevision hash
   `0x3cc7eaf6` in the versioncheck row is for the 1.29.2.9231 build
   tested here. Earlier 1.29.0/1.29.1 builds will compute different
   hashes and need their own entries. The `auth_req`, M2-dispatch,
   `LphChecked`, and `CreateAccount` byte offsets will likely differ
   across sub-versions because each is a recompile — the structural
   search techniques in §4 and §6 will re-derive them.

2. **Port the static EXE patches into a `dll_29/applyPatches`.** The
   `../w3l/dll_29/` directory is set up to host an in-memory patcher
   that applies byte changes at runtime (so the EXE on disk stays
   pristine and the Authenticode signature stays valid until load
   time). Currently `applyPatches` is a stub. The work is to copy
   the patch sites from this document into `patches.h` and wire
   them through `apply_patches(workerOpts->baseAddr, ...,
   section_size)` instead of the dead `LoadLibrary("Game.dll")`
   path that the 1.27/1.28 helpers use.

3. **Native Windows build of `build_payload.py`.** Currently requires
   a Linux toolchain (gcc-multilib + keystone). Could be ported to
   mingw-w64 on Windows.

## 11. The MOTD-W3 fmt bug

Encountered while testing 1.29 (the 1.29 client gets far enough to
request the W3 MOTD; older clients tested in CI may not). At
`src/bnetd/handle_bnet.cpp:2951`:

```cpp
fmt::format_to(serverinfo, "{}" + '\n', (line + 1));
```

`"{}"` is a `const char*`. `'\n'` is a `char` with value 10. So
`"{}" + '\n'` is **pointer arithmetic** — a pointer 10 bytes past the
start of the 3-byte string literal `"{}\0"`. This is undefined memory.
`{fmt}` reads it as the format string, sees what looks like positional
indices (`{0}`, `{1}`, ...), realises it doesn't have enough arguments,
and throws `argument index out of range` — which `fmt::format_to`
propagates as an unhandled exception, killing bnetd.

It only fired the first time bnetd parsed `bnmotd_w3.txt`. The crash
was reproducible on every fresh login of the test 1.29 client.

Fix: change `"{}" + '\n'` to `"{}\n"`. Trivial, but fundamentally was a
typo / misuse of C++ that survived in the tree because no integration
test exercises this path.
